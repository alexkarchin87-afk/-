# VoiceAgent — изменения в этой сборке

## Только телефон: убран Python-бэкенд, добавлены root-действия и быстрый ответ на уведомления

Пользователь прислал ТЗ на архитектуру "без сервера на ноутбуке" — только
телефон (рутованный OnePlus 13), Telegram и ключи DeepSeek/Claude.

**Убрано:**
- `backend/` (Python/FastAPI воркер для 3D-задач) и
  `integrations/apps3d/` (`RemoteWorkerClient`, `ThreeDOrchestrator`,
  `Job3D`) — единственная часть проекта, которая требовала постоянно
  запущенного процесса на ноутбуке/VPS. Ничего другого в проекте на это не
  опиралось (голосовой пайплайн, Telegram-бот, конспекты — всё и так было
  на телефоне), так что удаление ничего не задело.
- `AGENT_WORKER_URL`/`AGENT_WORKER_TOKEN` из `local.properties` и
  `app/build.gradle.kts`.

**Добавлено:**
- **Мгновенный переход к Claude** — "спроси Клода, ..." теперь идёт прямо в
  Claude одним сетевым вызовом, в обход DeepSeek-классификатора и черновика
  (`LLMClient.askClaudeDirect`). Дешевле по токенам, а не дороже — вместо
  потенциальных двух вызовов (черновик DeepSeek + проверка Claude) один.
- **Быстрый ответ на уведомление без открытия мессенджера** — "ответь Вике
  текст" использует собственное действие "Ответить" (RemoteInput) самого
  уведомления Telegram/WhatsApp — тот же механизм, которым пользуются
  Wear OS/Android Auto. VoiceAgent не обращается к API мессенджеров напрямую
  и не нужен отдельный бот-токен именно для этого (`NotificationReader.replyTo`).
- **Root-переключатели** (`system/RootActions.kt`) — "включи/выключи
  вайфай/блютус/мобильный интернет" через `su -c "svc ..."`. Сознательно НЕ
  сделан универсальный "выполни root-команду от LLM" — только фиксированный
  список из трёх переключателей, которые LLM выбирает по имени действия, а
  не пишет shell-строку сама. Открытый `su -c "$llmString"` означал бы, что
  любая инъекция в то, что попадает в промпт (текст уведомления, контент
  экрана), в теории получает root-выполнение произвольного кода — а это уже
  не ассистент, а дыра.
- **`install_app` — без тихой установки.** По просьбе в ТЗ была тихая
  фоновая установка apk по ссылке через `pm install -r` — этого не сделал: с
  root это буквально троянский приём скрытой установки кода, и root тут
  ничего не оправдывает. Вместо этого: имя приложения → открывает Play
  Маркет; прямая ссылка на `.apk` → скачивает файл и передаёт его
  системному экрану подтверждения установки (как при скачивании из
  браузера — один тап "Установить" всё равно обязателен).
- **Автозапуск при включении телефона** (`system/BootReceiver.kt`,
  `BOOT_COMPLETED`) — голосовой сервис и пузырь поднимаются сами, без
  захода в приложение.
- **Проверка root в диагностике** — `Diagnostics.kt` теперь показывает,
  есть ли вообще root-доступ, до того как команда "выключи вайфай"
  просто молча ничего не даст.
- Accessibility Service **не заменён** на root-ввод (`input tap`/`input
  swipe` через shell) — она и так уже работает, официально поддерживается
  и обратима одним тапом в системных настройках; менять рабочее решение на
  менее прозрачное без явной выгоды не стал.

## Полная проверка перед первым запуском на реальном телефоне (OnePlus 13)

Пользователь попросил перепроверить весь проект на работоспособность перед
первым запуском на настоящем устройстве. Прогнал статический анализ по всем
63 .kt-файлам (сверка деклараций классов/объектов с импортами, R.*-ссылок с
реально объявленными ресурсами, дублей имён) — серьёзных ошибок компиляции не
нашёл, кодовая база в порядке. Нашёл и починил две реальные проблемы, которые
проявились бы именно на живом устройстве, а не в теории:

1. **`SystemController.openApp` не находил бы установленные приложения** —
   на Android 11+ без блока `<queries>` в манифесте `PackageManager` скрывает
   от приложения большинство сторонних пакетов (ограничение видимости
   пакетов). Команда "открой Телеграм" молча ничего не делала бы на
   настоящем OnePlus 13 (Android 14/15), хотя код был написан правильно.
   Добавлен `<queries>` с `MAIN`/`LAUNCHER` intent-фильтром.
2. **Экран входа через Google мог намертво заблокировать доступ к
   собственному приложению** — `AccountManager.handleSignInResult` тихо
   проглатывал `ApiException` и возвращал `null` при любой ошибке, включая
   самую вероятную первопричину — незарегистрированный SHA-1 сборки в
   Google Cloud Console (без этого шага Google Sign-In выдаёт
   `DEVELOPER_ERROR` вообще без исключений в редких случаях). Теперь ошибка
   показывается текстом на самом экране входа, а рядом с ней — кнопка
   «Продолжить без входа», чтобы неполная настройка OAuth не запирала
   владельца телефона снаружи его же личного ассистента.

Добавлена новая функция — **самодиагностика** (`system/Diagnostics.kt` +
секция в `SettingsActivity` + голосовая команда «Ваня, всё работает?»):
разом проверяет микрофон, Accessibility, доступ к уведомлениям, оверлей,
оптимизацию батареи, наличие ключа DeepSeek и наличие Vosk-модели — с прямой
кнопкой в нужный системный экран на каждый проблемный пункт. Смысл: почти
все реальные проблемы первого запуска — это забытое разрешение или не
добавленная руками Vosk-модель, а не баг в коде; раньше единственным
признаком было молчание в логах.

Полный чек-лист первого запуска — в README.md, раздел "Чек-лист перед первым
запуском на реальном телефоне".

## Ещё один проход (память по приоритетам, конспекты, дайджест уведомлений, режим "что это")

Пользователь прислал текстовую спецификацию персонажа "Ваня" (память с
приоритетами P1/P2/P3, конспекты-конструкторы, дайджест уведомлений, два
режима анализа экрана) — она была написана для LLM-бэкенда в целом, а не для
конкретного ассистента-разработчика, так что я перенёс её в реальный код,
а не просто вставил текстом в системный промпт (иначе P1-факты ничем не были
бы защищены от случайного удаления моделью — только её добросовестностью).

**Память с приоритетами (P1/P2/P3)** — `core/UserMemory.kt` переписан:
- Теперь у каждого факта есть уровень: P1 (навсегда, снять может только явное
  "забудь"), P2 (по умолчанию — заменяемый), P3 не используется отдельным
  действием, но зарезервирован в коде на будущее.
- Неприкосновенность P1 обеспечена в коде (`enforceCapacity` трогает только
  P3), а не инструкцией модели — так надёжнее.
- `remember_fact` в `AgentOrchestrator.kt` получил необязательный `tier`:
  "запомни навсегда"/"сохрани железно" → P1, иначе P2.
- Старый плоский формат хранения фактов мигрируется автоматически при первом
  чтении (см. `KEY_FACTS_LEGACY`).
- `SettingsActivity.kt`: список "Что помню о тебе" показывает пометку
  "[навсегда]" у P1-фактов.

**Конспекты-конструкторы** — новый пакет `notes/`:
- `NotesBuilder.kt` — собирает конспект из одного или нескольких источников
  по фиксированным правилам оформления (ЗАГЛАВНЫЙ заголовок, иерархия
  1./1)/•, пояснения в скобках, вставка `![описание](файл)` для схем).
- `NotesStorage.kt` — по файлу на тему, чтобы "дополни конспект" находило
  нужный.
- Новые действия `notes_build {topic, sources}` и `notes_extend {addition,
  topic}` в `AgentOrchestrator.kt`. "Дополнить" — это отдельный проход через
  LLM с просьбой не пересказывать существующее заново, а не построчный diff
  (для реального diff’а внутри одного markdown-текста пришлось бы городить
  парсер структуры конспекта — LLM с чёткими инструкциями и просьбой вернуть
  файл целиком проще и достаточно надёжно для этой задачи).

**Дайджест уведомлений ("что нового?")** — раньше чипы "Что нового?" и
"Прочитай уведомления" в `MainScreen.kt`/`OverlayBubbleController.kt` были
декорацией: `NotificationReader` публиковал каждое уведомление отдельным
событием, но никто их не копил, так что ответить на "что нового" агенту
было решительно нечем.
- `system/NotificationBuffer.kt` — кольцевой буфer последних уведомлений
  (до 200 штук), заполняется из `NotificationReader`.
- `system/ChatsDigest.kt` — берёт всё, что накопилось с прошлого вызова,
  подставляет человекочитаемое имя приложения (через `PackageManager`) и
  просит LLM выдать 1-2 фразы по делу, без флуда.
- Новое действие `chats_digest {}`.

**Режим "что это" (энциклопедия) отдельно от "что делать" (навигатор)** —
раньше был только `describe_screen` (навигатор). Добавлен `identify_on_screen`
с отдельным промптом ("назови и дай справку, не пиши инструкцию"). Честная
оговорка в коде и в промпте: агент видит не скриншот, а только видимый текст/
подписи через Accessibility — если на экране нет текстовой подсказки, что это
за объект (например, фото без подписи), режим "что это" не сможет опознать
объект по одному только тексту. Полноценное распознавание по картинке
потребовало бы захвата экрана через `MediaProjection` — это отдельная,
более тяжёлая доработка, не сделанная в этом проходе.

## Новые функции (по запросу)

**"Что на экране и что делать" — пошаговая голосовая подсказка**
- Новое действие `describe_screen` в `AgentOrchestrator.kt`: читает видимые
  тексты и подписи элементов через уже существующий
  `SystemController.readScreen()` (Accessibility), отправляет их вместе с
  вопросом пользователя в LLM с просьбой дать короткую пошаговую инструкцию
  ("нажми…", "введи…"), озвучивает результат через TTS.
- Экран перечитывается заново при каждом вызове — в том числе на "а что
  дальше?" — а не берётся из памяти прошлого ответа, потому что мог
  измениться после предыдущего шага.
- Требует уже существующее разрешение Accessibility (Settings > Спец.
  возможности > VoiceAgent) — новый экран разрешений не добавлялся.

**"Что за музыка играет" + "добавь в избранное в Яндекс Музыке"**
- Новый файл `system/MediaSessionReader.kt` — читает метаданные (название,
  исполнитель) из активной медиасессии через `MediaSessionManager`. Работает
  для любого плеера с медиасессией (Яндекс Музыка, YouTube Music, Spotify,
  подкасты), не только для Яндекс Музыки.
- Использует уже выданное разрешение "Доступ к уведомлениям" — Android
  привязывает `getActiveSessions()` к включённому
  `NotificationListenerService`, а он у VoiceAgent уже есть
  (`NotificationReader`). Отдельного экрана разрешений не потребовалось.
- Новое действие `now_playing` — озвучивает, что сейчас играет.
- Новое действие `like_current_track` — открывает Яндекс Музыку (если там
  что-то играет) и нажимает кнопку "Мне нравится" через Accessibility
  (`SystemController.likeCurrentTrackInYandexMusic()`). Это управление
  реальным интерфейсом уже установленного приложения на телефоне
  пользователя — тем же механизмом, что и остальные системные действия
  (`tap_text` и т.п.), а не обращение к API Яндекс Музыки, официального
  публичного API для сторонних приложений у неё нет.
- Пробует несколько вариантов подписи кнопки подряд (текст на разных языках
  версиях интерфейса меняется) — если Яндекс Музыка обновит дизайн, список
  кандидатов в `SystemController.LIKE_LABEL_CANDIDATES` может потребовать
  правки.

## Попутный баг-фикс
`AccessibilityAgent.dumpVisibleText()` и `tapByText()` раньше читали только
`node.text` — а иконки без подписи (как раз кнопка-сердечко "лайка" в
музыкальных плеерах) на Android имеют только `contentDescription`, без
видимого текста. Без этого фикса ни описание экрана, ни лайк трека не могли
бы найти такую кнопку. Теперь оба метода проверяют оба поля.

## Ещё один проход (голосовая помощь по экрану + музыка)

Обе запрошенные фичи — «что на экране и что делать» и «что играет / добавь в
избранное в Яндекс Музыке» — в присланном архиве уже были полностью
реализованы (`describe_screen`, `now_playing`, `like_current_track` в
`AgentOrchestrator.kt`, плюс `SystemController.readScreen/nowPlaying/
likeCurrentTrackInYandexMusic`, `AccessibilityAgent.dumpVisibleText`,
`MediaSessionReader`). Похоже, кто-то (другая сессия/Claude Code) уже
собрал их до меня — код разумный, с честными оговорками в комментариях
про хрупкость UI-автоматизации Яндекс Музыки.

Что сделал в этом проходе:
- **Реальный баг** в `AccessibilityAgent.tapByText`: клик выполнялся по
  самому найденному узлу с нужным текстом/contentDescription, а во многих
  интерфейсах (в т.ч. вероятно в кнопке "лайка" Яндекс Музыки) кликабелен
  не сам текстовый/иконочный элемент, а его родитель — клик по
  некликабельному узлу молча ничего не делает. Добавил поиск ближайшего
  кликабельного предка перед кликом.
- Восстановил правки из прошлого прохода, которые не попали в этот
  архив (см. секцию выше): баг с тумблером оверлея в `MainActivity.kt`,
  устойчивый парсинг JSON-действия и ретраи 429 (уже были подхвачены в
  `AgentOrchestrator.kt`/`LLMClient.kt` этой версии — совпадение или тоже
  унаследовано), единый брендинг "Ваня" в `AgentSiriPanel.kt` (было
  только в Windows-виджете).
- Добавил "Что на экране?" и "Что сейчас играет?" в чипы быстрых команд
  (`MainScreen.kt`, `OverlayBubbleController.kt`) — раньше команды
  работали только по прямому голосовому/текстовому запросу, в подсказках
  их не было видно.

### Что стоит проверить вручную на реальном устройстве
`likeCurrentTrackInYandexMusic` — список подписей кнопки "лайк"
(`LIKE_LABEL_CANDIDATES` в `SystemController.kt`) подобран по вероятным
вариантам, но не проверен на реальном экране Яндекс Музыки — при первом
запуске стоит попробовать голосом и, если не сработает, посмотреть через
`readScreen()` (или Accessibility-инспектор), как реально подписана кнопка
в установленной версии приложения, и добавить точный вариант в список.

## v7: Правила разработки кода — кроссплатформенность, .exe для Windows, защита от путей

По прямому запросу — новые правила зашиты в промпты `CodeGenAgent`, а не
только описаны словами, чтобы реально влияли на генерацию, а не потерялись
при следующей правке.

### Кроссплатформенность (Android / Windows)
- **`agent/AgentOrchestrator.kt`** — `generate_code` теперь принимает третий
  параметр `platform` ("android" по умолчанию — код выполняется на этом же
  телефоне через Termux, как раньше; "windows" — LLM сама выставит его, если
  явно сказано "для компьютера/ноутбука" или речь о родственнике за ПК).
  `continue_code` платформу не трогает — она уже зафиксирована в самом
  сохранённом проекте.
- **`devassist/CodeGenAgent.kt`** — `generate(spec, platform)` выбирает один
  из двух системных промптов.

### Windows-проекты — всегда Python + GUI, готовые к сборке в один .exe
Новый промпт `createSystemPromptWindows` требует: только Python; GUI на
CustomTkinter или Flet (никакого голого консольного ввода-вывода); обязательный
`build.bat` с `pyinstaller --onefile --noconsole`; `requirements.txt` с
`pyinstaller` внутри; `run_instructions` в два шага ("дважды кликни build.bat
один раз" → "дальше просто открывай готовый .exe") — рассчитано на
родственника, который не будет ничего настраивать сам.

### Разворачивание абстрактных просьб в реальную логику
Добавлено общее правило (`sharedRules`, используется в обоих промптах и в
`revisePrompt`): на абстрактные/личные просьбы ("ИИ-человек, который понимает,
как прошёл день") — не делать голую заглушку, а самому продумать разумные
скрытые зависимости (системное время, сохранение состояния между запусками,
простой анализ тона по ключевым словам и т.п.). Это же правило продублировано
в описании действия `generate_code` в системном промпте самого оркестратора —
так формулировка "spec", которую он передаёт в CodeGenAgent, уже учитывает
скрытые требования, а не просто пересказывает фразу пользователя.

### Запрет на авто-вшивание стороннего софта в самого Ваню
- В `sharedRules` — явный запрет предлагать встраивание игр/чужого кода внутрь
  исходников самого VoiceAgent, патчить/пересобирать его APK и т.п.: LLM
  всегда пишет отдельный самостоятельный проект.
- **Реальное техническое ограждение, не только промпт** —
  `devassist/ProjectStorage.kt` теперь отклоняет пути файлов, которые пытаются
  выйти за пределы своей же папки проекта (`../../` и абсолютные пути), и
  очищает само имя проекта, прежде чем оно станет именем папки на диске
  (`devassist/ProjectNaming.kt`, `sanitizeProjectName`, используется и в
  `CodeGenAgent.parse`, и в `ProjectStorage.save` — синхронно, чтобы
  `lastGeneratedProjectName` в оркестраторе и реальное имя папки на диске
  никогда не разъезжались). Так даже если модель когда-нибудь ошибётся или
  промпт обманут, сгенерированный код физически не может дотянуться до кода
  самого VoiceAgent или чужих файлов на телефоне — это гарантия на уровне
  кода, а не только словесная просьба к LLM.

### Починка (важно)
Прошлый раунд обрывался на полпути — я сослался на `classifyCodeChoice`,
`handleRunNowChoice`, `CodeChoice` в `AgentOrchestrator.kt`, но не успел их
написать: проект в таком виде не собрался бы. Доделано:

### Роли Admin/User (пункт 2 из документа "Модуль экосистемы")

## Автоматическая маршрутизация DeepSeek/Claude вместо ручного выбора

В присланной версии уже была добавлена поддержка ключа Claude и модели
DeepSeek-R1, но переключение было РУЧНЫМ — тумблер в Настройках
(`LlmProvider`/`LlmProviderPicker`). Это ровно противоположно тому, что
просили: без выбора модели, с автоматическим определением сложности задачи.

Переделал `LLMClient.kt`:
- Убрал `LlmProvider`/`LlmPreferences` целиком (и тумблер в
  `SettingsActivity.kt`, и упоминания в `BackupManager.kt` — старое поле
  `llm_provider` в бэкапах старых версий просто молча игнорируется при
  импорте, ничего не ломает).
- `LLMClient.complete(...)` теперь сам решает: простой запрос — только
  DeepSeek-chat; сложный (эвристика `isComplexTask` по ключевым словам,

- Заодно опять исправил `CodeGenAgent.parse()` (хрупкий `removePrefix`

## Автосборка APK через GitHub Actions

В этой песочнице нет Android SDK и нет доступа в сеть (проверено — сборку
здесь запустить нельзя). Вместо этого добавил `.github/workflows/build-apk.yml`:
собирает debug APK на GitHub при пуше в main или вручную, кладёт готовый
файл в Actions → Artifacts. В репозитории нет закоммиченного
gradle-wrapper, поэтому workflow ставит Gradle 8.7 явно через
`gradle/actions/setup-gradle` и вызывает `gradle assembleDebug` напрямую
(не `./gradlew`) — если позже добавите wrapper в репозиторий, стоит
поменять на `./gradlew` для консистентности с локальной сборкой в Android
Studio. Секреты (DeepSeek/Claude/Telegram/MAX) в CI не нужны — сборка не
падает без них (см. `local.properties`/`getProperty(key, "")` в
`app/build.gradle.kts`), ключи вводятся уже в самом приложении после
установки.

## Мастерская сценариев — визуальный no-code конструктор (продолжение)

Реализовал полностью: модель (`workflow/WorkflowModel.kt`), хранилище
(`WorkflowStorage.kt`), исполнитель (`WorkflowRunner.kt` — переиспользует
`SystemController`/`TTSEngine`, не добавляет новой рантайм-логики), ИИ-сборщик
из текста (`WorkflowAiBuilder.kt`, идёт через forceComplex=true — тот же
путь DeepSeek-R1 + проверка Claude, что и кодогенерация), визуальный канвас
(`ui/workflow/WorkflowEditorActivity.kt`), интеграция в голос
(`run_workflow {name}`, `create_workflow {description}`, мгновенный запуск
по кодовой фразе до похода к LLM), точка входа в Настройках, Activity
зарегистрирована в манифесте.

Три реальных бага поймал и исправил по ходу:
1. `onMove` при перетаскивании блока стирал бы его params (data-class
   `copy()` делит ссылку на `MutableMap`, а не копирует — мой же неаккуратный
   `clear()+putAll()` из той же карты, которую сам только что очистил).
2. Линии связей на канвасе считались в сырых пикселях, а блоки отрисованы в
   `dp` — на экране с плотностью ≠1x (то есть почти на любом настоящем
   телефоне) линии не попадали бы в края блоков. Исправил через
   `DrawScope.toPx()` внутри Canvas (там доступна реальная плотность экрана).
3. Промпт `WorkflowAiBuilder` обещал, что `OPEN_APP.package` можно указать
   обычным именем приложения, а не то точным пакетом — но
   `SystemController.openApp()` умел резолвить только точный package name и
   молча падал на всём остальном. Вместо того чтобы просто убрать ложное
   обещание, реализовал реальную резолвку: `openApp` сначала пробует как
   точный пакет, а если не вышло — ищет среди установленных приложений
   (ACTION_MAIN/CATEGORY_LAUNCHER, не требует QUERY_ALL_PACKAGES) по
   видимому названию, сначала точное совпадение, потом частичное. Работает
   теперь одинаково и в обычных голосовых командах (`open_app`), и в блоках
   сценария — правил формулировку в основном системном промпте тоже, чтобы
   она отражала реальное поведение.

## Восстановление backend/ + .env

В присланном архиве папка `backend/` отсутствовала целиком (не только
`.env`) — восстановил её из предыдущей рабочей копии (`server.py`,
`requirements.txt`, `Dockerfile`, `docker-compose.yml`) и добавил то, чего
не было вообще: `backend/.env.example`.

Заодно нашёл и исправил реальную причину ошибки `uvicorn`:
- Команда `uvicorn main:app` не может сработать — FastAPI-приложение лежит
  в `server.py` (`app = FastAPI(...)`), правильно — `uvicorn server:app`.
- `.env` не подхватывался бы даже после создания при прямом запуске через
  голый `uvicorn` (в отличие от `docker-compose`, который сам читает
  `.env` в той же папке) — Python не читает `.env`-файлы сам по себе.
  Добавил `python-dotenv` в зависимости и `load_dotenv()` в начало
  `server.py`, плюс предупреждение в консоль, если токен так и остался
  дефолтным "change-me" — частая причина "вроде настроил, а не работает".

Проверил и честно поправил README: он утверждал, что `AGENT_WORKER_TOKEN`
можно вписать "в Настройках приложения" — неправда, на Android-стороне
вообще нет кода, который обращается к этому backend (ни поля в Настройках,
ни клиента) — `ThreeDOrchestrator`/`RemoteWorkerClient`, упомянутые в
комментариях `server.py`, не существуют. Это отключённая от приложения
заготовка сервера, интеграцию с телефоном ещё предстоит написать, если
она вообще понадобится.
