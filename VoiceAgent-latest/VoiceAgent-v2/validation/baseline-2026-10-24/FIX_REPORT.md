# VoiceAgent-v2 — разбор первого теста на устройстве

Дата: 24 октября 2026, Europe/Moscow.
База изменений: ранее подготовленный VoiceAgent-v2-ONEPLUS13.zip. Проверены реальные исходники этой версии, без отката к исходному P0-архиву. Запрос текущего этапа: STT, Telegram, текстовое поле. Предыдущие отчёты сохранены в validation/baseline-2026-10-23; они описывают прошлую версию.

## Состояние

Внесены ограниченные исправления в существующие реализации. Kotlin, JVM unit-тесты и Android Lint прошли. Новый APK НЕ собран: packaging останавливается на отсутствии Vosk-модели. Официальная загрузка в этой среде вернула HTTP 403 через proxy. Старый APK намеренно не включён как результат текущих исправлений. Устройства/эмулятора не было; работа на OnePlus 13 не подтверждена.

Статусы: CONFIRMED — доказано исходниками/артефактами/тестами; UNKNOWN — требуется устройство или сервер. Причины конкретного пользовательского сбоя нельзя окончательно установить без его APK и логов.

## 1. STT

**CONFIRMED, P1: отсутствующие ресурсы.** Фактический движок — Vosk Android 0.3.45. В предыдущем подготовленном APK нет assets/model-ru-small; libvosk.so присутствует, в том числе arm64-v8a. В исходниках этой версии модель также отсутствует. Это достаточная причина невозможности загрузки STT в этом APK, но не доказательство содержимого APK, установленного пользователем.

Файл → метод → причина → последствия → исправление → проверка:

- `app/build.gradle.kts` → `genVoskUuid`/упаковка APK → сборка допускала отсутствие модели, uuid мог существовать без модели → рабочая установка с неработающим STT → добавлена `verifyVoskModel` перед packageDebug/packageRelease → `assembleDebug` реально остановился с перечнем недостающих файлов. Компиляция, тесты и lint доступны отдельно.
- `scripts/download_vosk_model.sh` → загрузка/замена → отсутствие надёжной проверки HTTP и полноты нового архива перед заменой → риск удалить прежнюю модель при неудачной загрузке → curl --fail, проверка ZIP/основных файлов, staging и возврат прежней папки при неудачном перемещении → 3 файловых теста с подставным curl, без сети. PowerShell-скрипт в этой среде не выполнялся и не менялся.
- `app/.../system/Diagnostics.kt` → `checkVoskModel` → проверялся неверный внутренний путь и любое содержимое assets → ложное состояние модели → проверка основных непустых файлов и реального app-specific external пути. Наличие ресурсов явно отделено от успешной native-инициализации → компиляция/lint, тесты общего валидатора; Android UI диагностики не запускался.
- `core/ai-engines/.../STTEngine.kt` → `ensureModel` и новый `VoskModelLoader.load` → Vosk StorageService.unpack ловит IOException, но не все runtime/native-link ошибки; отдельные executor на вызов → ошибка могла не вызвать onError, loading оставался true; две STT-модели могли копироваться одновременно → один последовательный loader, прежний StorageService.sync, callback на main thread для Exception/LinkageError, безопасный stage-код в логах → компиляция и анализ байткода Vosk; реальные native-ошибки на устройстве НЕ воспроизводились.
- `VoskModelFiles.invalidateIncompleteCache` → одинаковый uuid заставляет StorageService.sync доверять неполному кэшу → повторная инициализация не восстанавливает отсутствующие файлы → удаляется только marker uuid неполного кэша, затем штатный sync перекопирует модель → JVM-тесты проверяют повреждённый/полный кэш, сохранность постороннего файла, форматы graph и путь.

Ресурсы ожидаются непосредственно в `app/src/main/assets/model-ru-small/` (am/, conf/, graph/, остальные файлы официального архива, uuid), без дополнительной вложенности vosk-model-small-ru-0.22. Реальный путь Vosk 0.3.45: `context.getExternalFilesDir(null)/model/model-ru-small`. Это подтверждено декомпиляцией используемого AAR. Отдельное разрешение на хранилище для этого каталога не нужно. RECORD_AUDIO уже запрашивается/проверяется; отказ микрофона — отдельная причина отказа захвата, не причина отсутствия assets.

**Осталось UNKNOWN:** содержимое установленного APK, native-совместимость модели, фактические разрешения и доступность external storage на OnePlus. Проверка структуры не доказывает корректность файлов модели. Полная модель в архив результата НЕ включена, её загрузка заблокирована средой. Используйте полную официальную модель, затем пересоберите APK; инструкция — DEVICE_DIAGNOSTICS.md.

## 2. Telegram

**CONFIRMED: встроенный код не реализует отвечающего на /start бота.** `TelegramClient` использует Bot API getUpdates/sendMessage. Polling запускается из `TelegramBotService.onCreate` через `MessengerBridge.startPolling`; сервис объявлен exported=false, но вызовов его запуска в приложении не найдено. Запуск VoiceAgentService сам по себе его не запускает. Webhook в этой интеграции отсутствует.

Входящее сообщение становится `AgentEvent.ActionRequested("messenger_received", ...)`. Обработчика этого события, отвечающего на /start, в AgentOrchestrator нет. Python `backend/server.py` обслуживает jobs/chat stream, Telegram polling/webhook/командный обработчик в нём отсутствует. Поэтому молчание встроенной интеграции на /start соответствует существующему объёму реализации. Автоответ и автоматический запуск сервиса НЕ добавлены, поскольку запрос запрещает новые функции. Если тестировался отдельно созданный/развёрнутый бот, нужны его исходники и логи сервера; его причина здесь UNKNOWN.

Подтверждённый дефект и диагностика:

- **P2, CONFIRMED:** `MessengerBridge.kt` → `pollTelegramLoop` → offset обновлялся до завершения suspend-публикации пакета → отмена могла подтвердить ещё не опубликованные сообщения → offset теперь обновляется после публикации и ensureActive → тест отмены при backpressure и перезапуска. Частично опубликованный пакет может повториться; exactly-once и сохранение offset после смерти процесса не заявляются.
- `MessengerBridge.kt` → `startPolling`/`stopPolling`/ошибки polling → добавлены безопасные события и классификация HTTP 401/403/409/429; при 401/403/409 пауза не менее минуты; transport/parse ошибки без exception.message/stack trace → тест конфликта 409, повторного start, stop, продвижения offset и отсутствия утечки синтетического токена.
- `TelegramClient.kt` → создание/sendMessage; `TelegramBotService.kt` → lifecycle → логируются только наличие настройки токена, lifecycle, HTTP status, ok. Значения токенов, URL, chatId, имена и тексты не логируются.
- Тест с /start подтверждает только публикацию входящего события и отсутствие автоматического ответа. Реальных обращений к Telegram в тестах не было.

Защита от повторного start в одном MessengerBridge сохранена и проверена. Конкурирующие процессы/внешний webhook без сервера проверить невозможно; 409 отражается как webhook_or_other_poller_conflict. Эти изменения не превращают интеграцию в отвечающего бота.

## 3. Поле «Спросите Ваню»

**CONFIRMED: реальная отправка существует.** Маршрут: Composer TextField/кнопка/IME → MainScreen.handleSendText → AgentControls.onSendText → MainActivity binder.sendText → VoiceAgentService.LocalBinder → AgentOrchestrator.handleTranscript(text, "text") → AgentEvent.Reply/Error → MainScreen.messages → UI. Называть кнопку отсутствующей или всегда неработающей оснований нет.

**P1, CONFIRMED:** при binder=null вызов `binder?.sendText` пропускался, а Composer очищал черновик и MainScreen добавлял сообщение в историю. До подключения сервиса пользователь мог потерять запрос без объяснения.

- `MainActivity.kt` → передача AgentControls, binding/stop/onDestroy → добавлена динамическая проверка готовности binder и учёт успешного bind отдельно от полученного binder. Ожидающий bind также снимается при закрытии/остановке.
- `VoiceAgentService.kt` → `LocalBinder.isReadyForText`/`sendText` → проверяются initFailed, job и инициализация orchestrator; безопасные accepted/rejected логи. Сигнатура sendText сохранена.
- `TextSubmission.kt`, `ChatComponents.kt` → submit → черновик очищается только после проверки готовности. Пустой ввод не отправляется.
- `MainScreen.kt` → handleSendText → до готовности Toast объясняет причину, текст остаётся; после готовности пользовательское сообщение/история записываются перед вызовом оркестратора, сохраняя порядок при немедленном ответе. Добавлены reply_displayed/error_displayed без содержимого.
- `AgentSiriPanel.kt`, `WindowsCornerPopup.kt` → параметр готовности передаётся в существующий Composer; desktop/phone/windows используют ту же проверку, параметры добавлены с default для совместимости.

Проверка: 4 JVM-теста готовности, сохранения черновика, однократной отправки, пробельного ввода; Kotlin/lint. Это unit-тесты функции отправки, НЕ Compose instrumentation и НЕ доказательство поведения всего UI на телефоне. Потеря UI-истории при пересоздании Activity и нерелевантные overlay-изменения в этот этап не включены.
